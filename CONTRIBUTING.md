# Contributing

Contributions of all sizes are welcome. The most useful one is a new service.

## Adding a service

The lexicons have to be [published](https://atproto.com/specs/lexicon#lexicon-publication-and-resolution) by the service itself. Pass the domain its NSIDs are under: `fm.teal.*` is `teal.fm`.

```bash
lex add teal.fm     # adds it to services.json and downloads its lexicons
lex build           # regenerates the package and the support list
lex lint            # checks the registry and the lexicons
```

If the service publishes under subdomains only (`_lexicon.feed.teal.fm` but no `_lexicon.teal.fm`), give it one of the NSIDs to start from:

```bash
lex add teal.fm --nsid fm.teal.feed.play
```

Commit `services.json`, `lexicons/`, `lexicons.lock.json`, `SUPPORTED.md` and `supported.json`, and open a pull request.

## How it is built

1. `services.json` lists the services and the repositories they publish lexicons in.
2. `lex fetch` resolves each service the way the Lexicon spec says (`_lexicon` DNS record, then the `com.atproto.lexicon.schema` records of that repository) and stores the schemas in `lexicons/`, unmodified. `lexicons.lock.json` records where each one came from.
3. `lex build` generates the `atproto_lexicons` package from them with the SDK's code generator, checks that it imports, and writes the support list.

The lexicons are committed so that every upstream change is a visible diff. The generated code is not committed; it is built for each release.

A scheduled job fetches the lexicons every day and opens a pull request when something changed. The bot merges it once CI passes, and merging publishes a new release. An update that removes lexicons or makes the support of a service worse waits for a review instead (`lex review`).

The fetched lexicons are untrusted. The jobs that fetch and build them hold no secrets; the pull request is opened, and the package published, by separate jobs that run none of that content.

## Development

The tooling needs Python 3.10+. `poetry install` puts the `lex` command into the virtual environment (`lexicons` is the same command under its long name).

```bash
poetry install
poetry run lex --help
```

| Command | What it does |
|---|---|
| `lex fetch` | Download the lexicons every service publishes. |
| `lex build` | Generate the package, write the support list, check that it loads. |
| `lex verify` | Only check that the generated package loads. |
| `lex lint [--fix]` | Check the registry and that the lexicons match it. No network. |
| `lex add DOMAIN` | Add a service and download its lexicons. |
| `lex status [DOMAIN]` | Show how well each service is supported. |
| `lex site [--serve]` | Build the website, and optionally serve it locally. |
| `lex review [--base REV]` | Tell whether an update can be merged without a review. |
| `lex version` | Print the version the next release gets. |

The published package is the `package/` folder. Its code is generated by `lex build` and is not committed.

```bash
poetry run pytest
poetry run ruff check . && poetry run ruff format --check .
poetry run pyrefly check
```

## Website

[lex.atproto.blue](https://lex.atproto.blue) is the `website/` folder plus a catalog that `lex site` generates into `site/`.

- `lex site --serve` builds it and serves it locally.
- `website/config.js` sets the searches it suggests, the names that drift behind the hero, how many rows it shows and its hotkeys.
- The link preview, the banner of the README and the icons are drawn from `design/og.html`, `design/banner.html` and `design/icon.html`. After editing one of them, `python design/render.py` rewrites `website/images/` and `website/favicon.ico`. It needs Chrome.
- The catalog carries the star count of the SDK, read from GitHub at build time (with `GITHUB_TOKEN` if it is set) and left out if GitHub does not answer.
- Pushes to `main` and a daily run deploy it to GitHub Pages.
